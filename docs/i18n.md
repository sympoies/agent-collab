# Languages

The viewer speaks English, Japanese and Traditional Chinese. The pattern is small on purpose, has
no runtime dependency, and can be copied to another UI repository.

## How it works

- **Catalog.** `src/i18n/catalog.ts` holds the English messages (the source of truth and the
  fallback). `src/i18n/ja.ts` and `src/i18n/zh-TW.ts` are typed `Messages`, so a missing or extra key
  does not compile. A message may use `{name}` placeholders and one plural form:
  `{count, plural, one {# item} other {# items}}`, where `#` is the count in the locale's digits.
- **Helper.** `t(key, params)` (from `useT()`) interpolates and chooses the plural form with
  `Intl.PluralRules`. A key missing in a locale falls back to English; an unknown key shows the key.
- **Choice.** `LocaleProvider` uses the saved choice, else the first supported entry of
  `navigator.languages`, else English. Detection matches whole subtags: `en` and `ja` (with any
  region), and Traditional Chinese for `zh-TW`, `zh-HK`, `zh-MO` and `zh-Hant` (with any further
  subtag, case-insensitively). Simplified Chinese (`zh`, `zh-CN`, `zh-Hans`) is not supported by
  design: it is skipped, so the next browser language is tried, and English is the last resort. The visible switcher saves the choice as a per-viewer
  preference in guarded storage (the page works when storage throws), and `<html lang>` follows.
  Dates and times in notices and tooltips use `Intl.DateTimeFormat` in the chosen locale
  (`formatDateTime`). The timeline's day separators and message times stay ISO 8601 and 24-hour in
  every language, on purpose: they are the same strings as the message ids and file names, so a
  reader can match them by eye, and a numeric order such as 04/11 versus 11/04 is never
  ambiguous. Changing this would be a deliberate product decision, not a translation fix.
- **What is never translated.** Message bodies, sender names, topics and file names come from the
  repository and are shown as they are. The catalog is the only place non-English text may live;
  documentation, comments, commits and pull requests stay English.
- **Tests.** `tests/i18n.test.ts` fails when a locale lacks a key, has an extra key, has an empty
  text or a mismatched placeholder, and checks interpolation, plural forms and language detection.

## What is translated, and what is not

Every user-visible string of the UI layer is in the catalog: labels, headings, buttons, accessible
labels and titles, notices, empty states, settings validation, relative times (`time.*`), sizes
(`size.*`) and dates (`formatDateTime`). Errors are worded from their kind and data
(`src/ui/errorText.ts`), never from the English `message` of the error object, which is for
developers and logs. Two things stay English on purpose: the technical diagnostics of the message
parser (for example "front matter is not closed"), which describe the repository's files, and the
composed live-demo notices (`live.*` built from several parts, for example "Still showing the
snapshot generated at ..."): one already on screen keeps the language it was made in until the
next action replaces it. Every other state (errors, refresh and folder messages, credential
warnings, file load errors) is stored as a catalog key or an error and worded when it is drawn, so
it follows a language switch at once; `tests/locale-provider.test.tsx` pins both behaviors.

`tests/i18n-strings.test.ts` parses the whole `src` tree and fails on JSX text, text attributes
(`aria-label`, `aria-description`, `aria-roledescription`, `aria-valuetext`, `title`,
`placeholder`, `alt`, `label`) and prose-like string literals that are not in the catalog. Prose
means more than one word, or one word with a capital (`"Loading"`, `"OK"`); a lowercase single word
is an identifier. Text passed to `Error`-like constructors, loggers, DOM lookups and storage is
developer-facing and skipped (the callee must match exactly). Excluded on purpose: `src/i18n`,
`src/demo` (repository fixtures), `src/message` (parser diagnostics), `src/source` (developer-facing
error texts; the UI words errors from kind and code) and `src/credentials`. A short allow-list in
the test holds proper names and abbreviations with a reason each; the scanner itself is tested.

## Adding a language

1. Add the code to `LOCALES` and its own-language name to `LOCALE_NAMES` in `src/i18n/catalog.ts`.
2. Copy `src/i18n/ja.ts` to `src/i18n/<code>.ts`, translate every value, keep the placeholders, and
   register it in `src/i18n/translate.ts` (`CATALOGS`) and in `detectLocale`.
3. Run `pnpm test`; the parity test lists what is missing. Check the phone layout in the browser
   suite (`pnpm test:browser`), which runs every locale in `LOCALES` at desktop and phone sizes.

## Adding a message

Add the English text under a new key, then the same key in every other catalog (the compiler
reports the ones you forgot), and use `t("the.key")` in the component. Do not build sentences by
joining fragments: word order differs between languages, so use a placeholder inside one message.
